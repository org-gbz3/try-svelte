# 0012. 開発環境の OpenTelemetry 受信・表示に .NET Aspire Dashboard を使う

## 状態

採用

## 背景

バックエンドに OpenTelemetry を導入し、ログ・トレースを出力する。その受け手として、トレースを表示し、
同じトレースのログへドリルダウンできるコンテナを Dev Container に追加する必要があった。

前提として以下を決めた。

- 用途は開発環境のみ。本番の監視基盤は別途検討する(アプリは OTLP で送るだけなので、送信先は環境変数で差し替えられる)。
- 保持は起動中だけでよく、永続化は不要。
- 1コンテナで手軽に構成する。
- 対象はバックエンドのみ。ブラウザーのトレースは、送信先の公開・CSP の `connect-src`・認証なしの受信口の扱いが必要になるため対象外。

## 検討した選択肢

- 案A: .NET Aspire Dashboard(`mcr.microsoft.com/dotnet/aspire-dashboard`)
  - 長所: 1コンテナで軽量、設定がほぼ不要。トレース詳細から同じトレースの構造化ログへ移動できる。.NET のログのカテゴリ・スコープが見やすい。
  - 短所: 保持はメモリのみで、件数の上限を超えると古いものから破棄される。
- 案B: grafana/otel-lgtm(Collector・Tempo・Loki・Prometheus・Grafana を同梱した1コンテナ)
  - 長所: ボリュームで永続化でき、Tempo から Loki へのリンクも設定済み。メトリクスも扱える。
  - 短所: 1GB前後と重い。今回は永続化が不要。
- 案C: OpenObserve
  - 長所: 単一バイナリで永続化でき、trace_id でログと相関できる。
  - 短所: 今回の条件(永続化不要)では案Aより利点が少ない。
- 案D: Jaeger
  - 短所: ログを扱えず、トレースからログへのドリルダウンができない。
- 案E: Collector・Tempo・Loki・Grafana を個別のコンテナで構成
  - 長所: 本番に近く、保持期間やリンクを細かく設定できる。
  - 短所: 4コンテナと設定ファイルが必要で、「1コンテナで手軽に」に合わない。

## 決定

案Aを採用する。イメージのタグは固定し、画面(18888)はホストのループバックにのみ公開、OTLP(gRPC 18889)は
compose ネットワーク内だけで受ける。ループバック限定の開発用途のため、ダッシュボードは匿名アクセスを許可する。

バックエンドは OTLP の送信先(`OTEL_EXPORTER_OTLP_ENDPOINT`)が設定され、`OTEL_SDK_DISABLED` が `true` でない場合だけ
OpenTelemetry を登録する。送信先は Dev Container の compose で設定し、設定ファイルには書かない。

## 理由

条件(開発のみ・永続化不要・1コンテナ・バックエンドのみ)を最も少ない設定で満たすため。
送信先が未設定の環境では計装を登録しないことで、本番・CI に影響を与えない。

テストは送信先が設定された Dev Container 内でも実行される。有効のままだと、テスト用ホストの終了ごとに
未送信データの送信を待ち、ダッシュボード停止中は1件あたり約20秒かかった。そのため、テストでは runsettings で
`OTEL_SDK_DISABLED=true` を設定して無効にする。

## 影響

- Dev Container に `otel-dashboard` サービスが追加され、`http://localhost:18888` でトレース・ログを確認できる。コンテナを停止・再作成すると内容は消える。
- DB のトレースは安定版がある `OpenTelemetry.Instrumentation.SqlClient` で取得する。EF Core 用の計装はベータ版のため採用しない。
- 永続化・メトリクスの長期保持・複数人での共有が必要になった場合は、案Bへの置換を別の ADR で検討する。アプリ側は送信先の変更だけで済む。
