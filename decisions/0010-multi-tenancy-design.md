# 0010. マルチテナント対応の構成

## 状態

採用

## 背景

これまでロール(`AspNetRoles`)と権限(`RolePermissions`)はシステム全体で1系統で、組織(テナント)の概念がなかった
([ASP.NET_Core_Identity.md](../ASP.NET_Core_Identity.md) 1節「テナント管理は未実装」、6節「組織単位の認可は今後の設計事項」)。
業務エンティティがまだ無い段階で分離の基盤を入れておくと、後から既存データへ `TenantId` を後付けする移行が不要になる。

決める必要があった論点は以下の通り。

- ユーザーとテナントの関係(所属モデル)
- テナント間のデータ分離方式
- テナントの作成・参加方法
- ロール・権限の範囲
- リクエストで対象テナントを特定する方法
- テナントロールの格納先

## 検討した選択肢

- 所属モデル
  - 案A: 共通アカウント(メールは全体で一意)で複数テナントに所属し、画面で切り替える
    - 長所: 既存のメール一意・パスキー・MFA・パスワード再設定をそのまま使える。
    - 短所: テナントごとに異なる資格情報や認証ポリシーを持てない。
  - 案B: テナントごとに別アカウント
    - 長所: テナント間でアカウントが完全に独立する。
    - 短所: ログイン時にテナント指定が必要になり、Identity の一意性・パスキーのRP・再設定フローを大幅に改修する必要がある。
  - 案C: 1ユーザー1テナント固定
    - 長所: 最も単純。
    - 短所: 後から複数所属にすると移行が発生する。
- データ分離
  - 案A: 共有DB + `TenantId` 列 + EF Core のグローバルクエリフィルター
    - 長所: マイグレーション・運用が1系統で済む。
    - 短所: 分離の強さがアプリ実装に依存する。
  - 案B: テナントごとに別DB
    - 長所: 分離・個別バックアップ・顧客単位の削除が容易。
    - 短所: 接続文字列の切り替え、テナント数分のマイグレーション適用、テナント作成時のDBプロビジョニングが必要。
  - 案C: 共有DB + テナント別スキーマ
    - 長所: 中間的な分離。
    - 短所: EF Core のスキーマ動的切り替えとモデルキャッシュの扱いが難しく、SQL Server 固有の運用が増える。
- 作成・参加
  - 案A: 運営者が作成し、テナント管理者がメールで招待する
  - 案B: ログインユーザーがセルフサービスで作成し、招待する
  - 案C: 運営者が作成し、既存ユーザーを直接割り当てる(招待なし)
- ロール範囲
  - 案A: システム(運営者)とテナントの2層
  - 案B: テナントごとのロールのみ
  - 案C: ロール定義は全テナント共通で、割り当てだけテナント単位
- 対象テナントの特定
  - 案A: URLパス(`/api/tenants/{tenantId}/...`)
  - 案B: Cookie・セッションに「現在のテナント」を保持する
  - 案C: サブドメイン
- テナントロールの格納先
  - 案A: `AspNetRoles` に `TenantId` を追加して再利用する
  - 案B: 専用テーブル(`TenantRoles` ほか)

## 決定

- 所属モデルは案A(共通アカウント + 複数所属)。
- データ分離は案A(共有DB + `TenantId` 列 + 名前付きグローバルクエリフィルター `Tenant`)。
- 作成・参加は案C(運営者が作成し、既存ユーザーを直接割り当てる)。
- ロール範囲は案A(既存の `Admin.*` をシステムロールとして残し、テナントロールを追加する)。
- 対象テナントはURLパスで特定する(案A)。
- テナントロールは専用テーブルに格納する(案B)。
- 非所属テナントへのアクセスは `403` とする。

## 理由

- 所属モデル・データ分離は、既存の認証機能(メール一意・パスキー・MFA・再設定)と単一DBの運用を崩さずに済む案を選んだ。
  分離がアプリ実装に依存する短所は、`ITenantOwned` を実装したエンティティへクエリフィルターを一括適用し、
  保存時にも `TenantId` を検証することで、個々のクエリでの条件の書き忘れが漏えいにつながらないようにして補う。
- 作成・参加は、招待の期限・使用済み判定・メール配送を作らずに済む最小構成を選んだ。セルフサービスで作成できる必要が出た場合や、
  招待が必要になった場合は見直す。
- ロールを2層にしたのは、テナント作成など全体の管理を既存の `Admin.*` 権限にそのまま任せ、業務の権限はテナントごとに変えられるようにするため。
- URLパスで特定すると、複数タブで別テナントを同時に開いても混線せず、Cookie・CSRFの設計を変えずに済む。
  サブドメインはパスキーのRP ID(`Email:PublicBaseUrl` のホストから導出)・Cookieドメイン・CSPに影響するため採用しなかった。
- `AspNetRoles.NormalizedName` はシステム全体で一意のため、再利用すると別テナントで同名ロールを作れない。
- 認可は [0001](0001-role-based-authorization-design.md) と同じく所属・テナントロールをCookieに載せず、リクエストごとにDBで判定する。
  所属解除やテナントロールの変更が既存のログインセッションへ即時反映される。
- tenantId は推測困難なGUIDのため、存在の秘匿(`404`)より既存の `401`/`403` の区別との一貫性を優先した。

## 影響

- テーブル `Tenants`・`TenantMemberships`・`TenantRoles`・`TenantMemberRoles`・`TenantRolePermissions` と、
  `PermissionActions.Scope` 列が追加される(マイグレーション `AddMultiTenancy`)。
- テナントに属するエンティティは `ITenantOwned` を実装し、APIは `/api/tenants/{tenantId}` 配下に置いて
  `[RequireTenantPermission]` または `[RequireTenantMember]` を付ける。
- 権限キーは `[PermissionKey]` の `PermissionScope` でシステム用とテナント用に分かれ、システムロールにはテナント用の権限キーを設定できない。
- テナントを横断して参照する処理(所属テナント一覧など)は `IgnoreQueryFilters` を明示する必要がある。個別テナントを扱う運営者APIはルートに `{tenantId}` を含め、テナント文脈を設定してフィルター・保存時の検証をそのまま効かせる。
- テナント作成時に既定ロール「テナント管理者」(その時点の全テナント用権限キーへの `Write`)を作成し、作成直後のテナントに管理できる人がいない状態を避ける。後から追加された権限キーは既存の既定ロールへ自動付与しない。
- `TenantMemberRoles` から `TenantRoles` への外部キーは、SQL Server が連鎖削除経路の重複を拒否するため連鎖削除にしていない。
  テナントロールを削除するときは、割り当てを先に削除する。
- テナント内のデータ量が大きくなり、分離の強さや個別バックアップが必要になった場合は、テナント別DBへの移行を別のADRで検討する。
