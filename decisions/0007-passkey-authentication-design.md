# 0007. パスキー(WebAuthn)認証の設計

## 状態

採用

## 背景

パスキー(WebAuthn/FIDO2)認証を追加したいという要望があった。`ASP.NET_Core_Identity.md` はこれまでパスキーに一切言及しておらず、MFA・外部ログインも未実装のまま「今後の判断事項」として扱われていた。

調査の結果、この案件が使う ASP.NET Core Identity 10(net10.0)には、パスキー登録・認証の組み込みサポート(`UserManager<TUser>.AddOrUpdatePasskeyAsync`/`GetPasskeysAsync`/`RemovePasskeyAsync`、`SignInManager<TUser>.MakePasskeyCreationOptionsAsync`/`PerformPasskeyAttestationAsync`/`MakePasskeyRequestOptionsAsync`/`PasskeySignInAsync`)が既に用意されており、暗号処理(チャレンジ生成・署名検証)は全てIdentity側が行う。公式ドキュメント([Enable Web Authentication API (WebAuthn) passkeys](https://learn.microsoft.com/en-us/aspnet/core/security/authentication/passkeys/?view=aspnetcore-10.0))によれば「登録済みパスワードアカウントへのパスキー追加」「パスキーのみでの新規登録」「パスキーのみでのログイン」の3シナリオを想定しているが、パスキーは2FA(第2要素)としては扱われない設計になっている。

以下4点は、実装前にユーザーへ確認して合意した方針。

## 検討した選択肢

### 1. パスキーの位置づけ(MFAか、パスワードに並ぶ代替の主認証手段か)

- 案A: パスワードに並ぶ代替のログイン手段として実装する。
  - 長所: Identity のパスキー実装自体がこの用途(単独の主認証要素)を想定して設計されている。要望通りの「パスキー認証」を素直に実装できる。
  - 短所: MFAの強度(パスワード+追加要素)は得られない。
- 案B: 将来のMFA(パスワード成功後の追加認証)の一部として組み込む。
  - 長所: パスワード漏洩時の防御力が上がる。
  - 短所: Identityのパスキー実装に2FA向けの組み込みサポートがなく、独自に「パスワード成功→追加認証待ち」の状態管理を実装する必要があり、実装・UXの複雑さが大きく増す。

### 2. 初回登録の本人確認方法

- 案A: ログイン済みユーザーのみ、設定画面から追加登録できるようにする。
  - 長所: 既存のパスワード認証で本人確認済みの状態でのみ強力な認証情報を追加できる。パスキーは常にパスワードに追加される形になるため、パスキーを全て失っても既存のログイン・パスワード再設定がそのまま復旧経路として使える。
  - 短所: パスキーのみでのアカウント作成はできない。
- 案B: サインアップ時にパスキーのみでアカウント作成できるようにする(パスワードレス登録)。
  - 長所: パスワード入力そのものをなくせる。
  - 短所: `RequireConfirmedEmail = true` のもとでのメール確認との整合、パスキーを全て紛失した場合の復旧手段(回復コード等)を別途設計する必要があり、実装・UXが複雑になる。

### 3. 本人確認(user verification)の要求レベル

- 案A: `UserVerificationRequirement = "required"`。
  - 長所: 生体認証・PINなどの本人確認を必須にでき、単なる「所持」だけでの認証を防げる。セキュリティ最優先の要望に合致する。
  - 短所: 本人確認に対応しない一部の古いセキュリティキーが使えなくなる。
- 案B: `"preferred"`。
  - 長所: 対応デバイスの幅が広がる。
  - 短所: 認証器によっては本人確認なしで通ってしまう。

### 4. 複数パスキーの管理UI(一覧・削除)の実装範囲

- 案A: 一覧・追加・削除ができる管理画面まで実装する。
  - 長所: 紛失した端末のパスキーを個別に失効できる。公式ドキュメントも「認証器モデルに脆弱性が発覚した場合の失効」を運用上の考慮事項として挙げている。
  - 短所: 実装範囲が広がる(新規ルート・新規API3本)。
- 案B: 追加のみ(1ユーザー1パスキー、置き換え方式)。
  - 長所: 実装範囲を最小化できる。
  - 短所: 紛失端末のパスキーを個別に無効化できず、複数端末での利用もできない。

## 決定

1. パスキーはパスワードに並ぶ代替の主認証手段として実装し、MFAとしては実装しない(案A)。
2. パスキーの初回登録は、ログイン済みユーザーが `/settings/passkeys` から追加登録する方式のみとし、パスワードレスでのアカウント作成には対応しない(案A)。
3. `UserVerificationRequirement = "required"` とする(案A)。
4. 一覧・追加・削除ができる管理画面(`/settings/passkeys`、`GET`/`POST`/`DELETE /api/auth/passkeys`)まで実装する(案A)。

加えて、実装に伴い以下も決定した:

5. Relying Party ID(`IdentityPasskeyOptions.ServerDomain`)は、Hostヘッダーからの暗黙推定に頼らず、既にメールリンク生成で検証済みの `Email:PublicBaseUrl` のホスト名から明示的に導出する。公式ドキュメントが「本番ドメイン確定前の登録→後からの `ServerDomain` 変更は既存パスキーを無効化する」ことを明記しているため、新しい設定項目を増やさずに既存の検証済み設定を再利用する。
6. 1ユーザーあたりの登録上限を10件とする(公式ドキュメントが推奨するDB枯渇攻撃対策)。
7. ログイン用オプション取得(`POST /api/auth/passkeys/login-options`)はメールアドレス指定の方式とし、discoverable credential + conditional UI(メール入力なしのオートフィル方式)には対応しない。これにより、応答の内容(許可される認証情報の有無)からアカウントの存在・パスキー登録有無が、ブラウザー側の挙動を通じて推測されうるという、WebAuthnの仕様に起因する限界を受け入れる。`resend-confirmation`/`forgot-password` で徹底している「応答からアカウント状態を判別できないようにする」方針とは完全には一致しないが、プロトコル上避けられない制約であり、今回のスコープでは discoverable credential 対応(将来の拡張)を見送る。

## 理由

- 1点目・2点目: 「利便性よりセキュリティを重視したい」という要望はあるが、パスキーは登場した時点で十分に強い認証(公開鍵暗号+デバイス内本人確認)であり、これをMFAの一部として組み込む複雑さに見合うセキュリティ向上は、まず単独の代替ログイン手段として提供する初期スコープでは正当化できないと判断した。またパスワードを常に残す設計にすることで、パスキー紛失時の復旧手段([decisions/0006](0006-password-reset-design.md)のパスワード再設定)をそのまま使い回せ、新たな復旧フローの設計が不要になる。
- 3点目: セキュリティ優先の要望に直接応える設定であり、公式ドキュメントもデフォルトのままでは`preferred`寄りになりがちな本人確認レベルを、明示的に`required`へ強めることを推奨している。
- 4点目: 端末紛失時にパスキーを個別に無効化できないと、実運用上のリスクが残ったまま公開することになるため、最初から管理画面を含めることにした。
- 7点目: discoverable credential/conditional UI対応は、メール入力を省略できる利便性向上と引き換えに、フロントエンドのログイン画面の作り直し(オートフィルUI)が必要になる別スコープの変更であり、今回は見送った。

## 影響

- `backend/Program.cs` に `IdentitySchemaVersions.Version3` の指定と `IdentityPasskeyOptions` の構成が追加される。
- `backend/Data/Migrations` に `AddPasskeySupport` マイグレーション(`AspNetUserPasskeys` テーブル追加、および Identity スキーマ v3 に伴う一部列の型変更)が追加される。配備順序として、マイグレーション適用後にパスキー機能を公開する必要がある。
- 将来、discoverable credential/conditional UI対応や、パスキーのみでのアカウント作成に対応する場合は、この決定を見直し、新しいADRを追加した上でこのADRを「廃止・置換」にする。
